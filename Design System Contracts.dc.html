EVALUATION: DS CONTRACTS

Three design systems, written as contracts

The ds-contracts proposition is that a design system's source of truth should be neither the Figma file nor the code, but a machine-readable contract that generates both. To evaluate it, I wrote Custard, Mark and Yapily UI as contracts and looked at what the format could and could not hold.

Fourteen component contracts, seven DTCG token files, three configs. The six Yapily UI contracts are extracted from the stylesheet that shipped in 2020; the Custard and Mark contracts are written from the systems as they stand. Below is what each system looks like when its components are described as data. The live component on the left, the contract that specifies it on the right.

What a contract holds

One JSON file per component: props and their legal values, anatomy (the parts and how they lay out), which token paints which channel, states, and accessibility semantics. It does not hold hooks, handlers, data fetching, or anything that only exists at runtime.

That cut is the interesting part. Writing three systems into it forced me to say out loud which of my design decisions were canvas-expressible facts and which were rules I had been keeping in prose. The "no more than six icon tiles per band" kind of rule that no schema has a field for.

contracts/button.contract.json
{
  "id": "yui.button",
  "status": "extracted",
  "source": { "file": "yapilyui.css",
              "lines": "2000–2160" },
  "props": [{
    "name": "variant",
    "type": { "enum": ["primary", "secondary",
                       "destructive", "likea"] },
    "default": "primary"
  }],
  "anatomy": { "root": {
    "tokens": {
      "background-color":
        "{color.action.{variant}.background}",
      "border": "{border.width.default} solid
                 {color.action.{variant}.border}",
      "border-radius": "{radius.control}",
      "padding": "{space.inset.control}"
    },
    "states": {
      "hover": {
        "background-color": "{color.surface.raised}",
        "color": "{color.action.{variant}.background}"
      },
      "active": {
        "background-color":
          "{color.action.active.background}",
        "animation": "pulse {motion.press} ease"
      },
      "disabled": { "opacity": "{opacity.disabled}" }
    }
  }},
  "a11y": { "notes": "No min-height is set, so
    short labels can fall under 44px." }
}

Writing the contract is what surfaced the focus problem. In the stylesheet, input:hover and input:focus sit four lines apart and declare the same border. Side by side in a state matrix, two identical rows are hard to miss.

  "status": "extracted",
  "semantics": { "element": "a", "role": "link" },
  "props": [
    { "name": "logo", "type": "image",
      "description": "Capped, not scaled to fit:
        max-height 40px, max-width 256px." },
    { "name": "layout",
      "type": { "enum": ["row", "tile"] },
      "default": "row" }
  ],
  "anatomy": { "root": {
    "layout": { "display": "grid",
                "word-break": "break-word" },
    "states": {
      "hover": { "border-color":
                 "{color.border.strong}" }
    },
    "parts": {
      "logo": { "tokens": {
        "max-height": "{size.logo.list}",
        "max-width": "{size.logo.max-width}" }},
      "meta": { "element": "small",
                "tokens": { "margin-bottom": "0" }}
    }
  }}
}

The logo cap is the load-bearing decision in this component. Banks supply wordmarks and icons at whatever size they hold them, so the row constrains both dimensions and lets the logo sit where it lands, rather than forcing everything into a square tile.

Custard

cst.*

The white-label consent journey. A customer supplies four values and a logo; everything else is fixed. That contract is a nine-line token file, and the fact that it is that short is the whole point. Widening it is how a white-label system stops being one.

tokens/theme.tokens.json
{
  "theme": {
    "color-action-primary": {
      "$value": "{color.ink}",
      "$description": "Primary button,
        focus ring, selected row tint." },
    "color-text-inverse": {
      "$value": "{color.white}" },
    "color-bg-canvas": {
      "$value": "{color.canvas}" },
    "layout-modal-radius": {
      "$value": "{radius.600}" }
  }
}

Everything else: spacing, type scale, the 44px targets, the structure. Lives in files the customer never sees.

contracts/payment-summary.contract.json
{
  "id": "cst.payment-summary",
  "anatomy": { "root": { "parts": {
    "amountBlock": { "tokens": {
      "font-size": "{font.amount.size}" }},
    "card": { "parts": {
      "payeeRow": {}, "accountRow": {} }},
    "legal": { "content":
      { "prop": "authorisation" }},
    "footer": { "slot": {
      "name": "footer",
      "accepts": ["cst.button-footer"],
      "required": true
    }}
  }}}
}

The legal part sits above the footer slot in the anatomy, so "the legal text goes above the button" is structural rather than a convention someone can forget.

contracts/feature-card.contract.json
{
  "id": "mrk.feature-card",
  "props": [{
    "name": "band",
    "description": "Which band the card
      sits on. Decides whether it
      carries a rule.",
    "type": { "enum": ["paper", "panel"] },
    "default": "paper"
  }],
  "anatomy": { "root": { "parts": {
    "tile": { "component": {
      "id": "mrk.icon-tile",
      "props": { "glyph":
        "account_balance" } }},
    "title": {}, "body": {}
  }}}
}

"No border on paper bands, 1px rule on panel bands" only survives as a contract if the card knows which band it is on. So the band became a prop: a decision the format forced, and the right one.

What the format could not hold

Composition budgets

"Never more than six icon tiles per band." "Two panel tints maximum per page." "No more than two buttons per band." Every one of these is a real rule that shaped the system, and none of them has a field. They survive only as description prose that nothing enforces.

Responsive geometry

Custard's modal is 960 / 760 / full-bleed with radius 24 / 20 / 0, and its rows are 64 / 60 / 56. I encoded that as a density variant, which is honest on the canvas but wrong in code. In code it is a media query, not a prop. The format made me pick the surface I cared about more.

Copy as data

Custard's footer has twelve variants because consent copy differs by product and region. Product and region are props; the label is a separate text prop. Nothing in the contract states that the first two determine the third, so the relationship that makes twelve variants tractable is the part that did not travel.

The things it held better than I expected

Slot constraints (accepts: ["cst.button-footer"]) turn "do not redecide the button geometry per screen" into something a build can refuse. Anatomy ordering makes "legal copy above the button" structural. And a four-value theme file is a much better statement of a white-label contract than the page of prose I had been maintaining.

Caveats

These contracts were written by hand against the repository's example files, not validated against its 31KB schema, and never run through generate. Expect field-level corrections on first contact with the real validator.

Eleven components out of roughly forty across the three systems, chosen as the tractable ones. On the repository's own accounting that is the honest way to read any coverage number: the easy fraction first, the average second.
